# v0.0.3: packages installed during a run

Policy: the model may install packages from PyPI during the run through bash; nothing is pre-installed or named.

## Evidence

About half of the sessions that installed a Python package through bash and then imported it in the persistent REPL
still got `No module named`. On the benchmark Mac the interpreter is `/usr/bin/python3` (3.9.6) with a non-writable
site-packages, so 20 of 50 sessions saw `Permission denied` or `externally-managed`, and installs into a venv, a
`--target` directory or the user site were invisible to the sandboxed worker, which may read only the interpreter's
`sys.path` roots as they were at start.

## Reproduction (local wheel, offline, `factr-learn/tests/install_then_import.rs`)

The worker is started once, a cell imports `dummyprobe_pkg` (fails), a subprocess installs it, the cell runs again
without a restart.

| Variant | Before | After |
| --- | --- | --- |
| `pip install` into the venv the worker runs on | imports | imports |
| `uv pip install --python <venv python>` | imports | imports |
| `pip install --user` (user site created after start) | `No module named` | imports |
| install into a different venv than the worker's | `No module named` | `No module named` (the hint now names the worker's own interpreter) |

The first two were not broken in an unsandboxed worker; under the macOS sandbox a user-site directory created after
start was also unreadable, which `read_roots` now allows in advance.

## Changes

1. `python_worker.py`: `_refresh_imports()` before each cell: `importlib.invalidate_caches()`, and
   `site.addsitedir` for a user-site or site-packages directory that now exists and is not on `sys.path` (stat calls only).
2. Session environment (`factr-base/src/python_env.rs`): at start, unless `FACTR_REPL_PYTHON` is set,
   `FACTR_GUARD_SESSION_VENV=0`, or the base python is already a virtualenv, make one venv with
   `uv venv --seed --system-site-packages` (else `python3 -m venv --system-site-packages`) under the temp directory,
   put its `bin` first on `PATH`, set `VIRTUAL_ENV` and `FACTR_SESSION_VENV` (reused if already set). The REPL,
   the environment line, bash `python`, `python3`, `pip` and `uv pip install` all resolve to it, and the sandbox reads
   its site-packages. It is made eagerly at start (about a second without uv, well under that with it), not at first
   REPL start, because bash needs it on `PATH` from the first command. It is not removed at exit. When the REPL is on
   is unchanged (Linux still needs `FACTR_REPL_PYTHON`).
3. `missing_module_hint` names one command (`uv pip install --python <py> <pkg>`, else `<py> -m pip install <pkg>`)
   plus the standard-library fallback; `install_failure_hint` adds one line after a structurally failed install.
   Nothing is ever installed for the model.

## Lifetime and cost of the session venv

- Removed by `shutdown::cleanup` (SIGTERM/SIGINT and the runtime's own shutdown) and by the exit guard in `main`; only
  the venv this process made, never an inherited `FACTR_SESSION_VENV`. A directory removal, a few ms.
- At start, `factr-session-venv-<pid>` directories in the temp dir whose pid is gone (`kill(pid, 0)`), owned by the
  current user, real directories, exact name pattern, are removed (`sweep_stale_session_venvs`).
- The build runs on a background thread started at engine start (`VenvGate`), so the ready line is not held up:
  ready time median 0.15 s (v0.0.2 0.14 s, guard off 0.14 s, no-uv 0.17 s; 5 runs each; the synchronous build of the
  earlier 0.0.3 commit measured 2.6 s with uv and 2.2 s without). The first launch of a freshly copied binary costs
  about 1-2 s of OS scan in every variant; that is not the venv.
- The path is deterministic (`<tmp>/factr-session-venv-<pid>`), so `PATH` (venv `bin`, then the `python` shim, then the
  original entries), `FACTR_SESSION_VENV` and `VIRTUAL_ENV` are set at start. Everything that needs the venv waits on
  `ensure_session_venv(15 s)`: the first bash command (before the command is built), the REPL tool (before the cell
  starts, so the cell's compute cap does not count the wait), every REPL worker start (the host resolves the
  interpreter then), `python_env::interpreter()` (environment line, hints), `snapshot()` itself as its first step (so
  `have`/`missing`/`installers` are all computed after the venv exists; before, the tool list was read first and the
  installers after, giving `installers: uv,pip,pip3; ... missing: pip`), the auto-verify gate's shell, and the `!` shell.
  Free once the build is finished. Not gated: MCP stdio servers and cron scripts (they do not depend on the venv).
- Failure (no uv and no `python3 -m venv`, an unwritable temp dir, a creator that errors): the gate releases at once,
  the half-built directory is removed, a warning is logged once, and bash/REPL use the system interpreter with the old
  hint. The engine does NOT rewrite its own environment from the build thread (`setenv` from a non-main thread is
  unsafe while others read the environment): `PATH`/`VIRTUAL_ENV`/`FACTR_SESSION_VENV` keep their values, a missing
  `bin` on `PATH` is skipped by lookup, and each command the engine starts (`bash`, background and detached shells, the
  auto-verify gate, the `!` shell) gets `PATH` without the venv `bin` and the two variables removed for that command
  only (`python_env::withdrawn_path`); readers (`session_venv_active`, `session_venv_python`, the install hint) check
  the gate and the directory. A build that is still running after 15 s is cancelled (its process group is
  killed) and removed, a late result never revives it; the session continues on the system interpreter.
- Shutdown during the build (SIGTERM, exit): the creator's process group is killed and reaped, the venv directory and
  its private TMPDIR are removed. The creator runs with its own `TMPDIR` (`<venv dir>-build`) because `ensurepip` left
  a `tmp*cacert.pem` in the shared one; that file came from our no-uv build (v0.0.2 never creates a venv) and is gone now.
  A SIGTERM before the signal handler is installed (the first few ms) still leaves the directory for the next start's sweep.
- Cleanup: removed at shutdown and exit; stale `factr-session-venv-<pid>[-build]` of dead engines are swept at start.
  Engine RSS is unchanged (about 28.8 MB at ready, 29.5 MB after 2 s); the build runs in a child that is waited on.

## Tests

Background build: `VenvGate` unit tests with injected creators (start does not block; gate waits then proceeds; failing creator releases promptly and cleans up; a creator past the bound is abandoned and its late directory removed; shutdown during creation kills the child group and removes the directory). `factr-app-core` `session_venv_gate_tests`: with a slow fake creator the first bash command and the first REPL cell block on the gate and then see the venv with a preinstalled package; a failing creator falls back to the system interpreter. Real binary (scratch scripts): ready time, first bash and first REPL call right after ready, fake-uv failure and hang, SIGTERM 0.3 s and 0.6 s after start with no stray directory or process.

`factr-learn/tests/install_then_import.rs` (variants above), `factr-learn/tests/session_venv.rs` (made once, reused,
bypassed by `FACTR_REPL_PYTHON` and the guard, install then import in the sandboxed REPL without a restart, hint names
the venv python), stale-sweep unit test in `python_env.rs` (a dead-pid directory is removed; a live pid, a non-numeric name and an unrelated directory are kept), other unit tests in `python_env.rs` and `shell.rs`. First-request prefix is unchanged (all new text is tool output).
